# Feature: Content Storage and Historical Reconstruction

- **Status:** Partial. Core text reconstruction is verified; indexed event-range reads and snapshot seeking are implemented with bounded event/byte limits. The VS Code host path is covered by core equivalence tests but no interactive host stress test for very large sessions has been run.
- **Related architecture:** [Content-addressed storage](../../ARCHITECTURE.md#6-content-addressed-storage), [Historical reconstruction](../../ARCHITECTURE.md#8-historical-reconstruction)

## Problem

An event history is useful only when Parallax can reliably recover the text content that existed at a selected point in time. Repeated content should not needlessly multiply storage, and corrupted or missing records must not produce misleading output.

## Goals

- Identify supported text-file content with SHA-256 hashes.
- Persist content and event references locally.
- Generate unified diffs and added/removed line statistics.
- Reconstruct historical file content from the available history and snapshots.
- Preserve data integrity and explicit failure behavior.

## Non-goals

- Binary-file reconstruction.
- Claiming exact full-workspace reconstruction without a complete workspace manifest.
- Silent normalization of line endings, whitespace, or encoding.

## Functional requirements

1. Content fingerprints follow one documented byte-encoding contract.
2. A content reference resolves to the same bytes that were originally stored.
3. Where deduplication is implemented, identical content under the same encoding contract is stored once per defined deduplication scope.
4. File paths and content hashes remain separate identifiers.
5. Diffs can be generated for supported text-file versions.
6. Historical reconstruction uses a well-defined event order and available snapshots/content records.
7. Indexed reconstruction reads events after the nearest valid snapshot and fails clearly when the required range exceeds 100,000 events or 64 MiB.
8. Missing or corrupt data produces an explicit reconstruction error.
9. Read-only history inspection does not modify the active workspace.

## Failure behavior

- Missing blob: report the missing content reference and the affected reconstruction point.
- Hash mismatch: report integrity failure; do not return the content as valid.
- Invalid patch: fail reconstruction or use a verified alternative anchor if the implementation supports one.
- Unsupported/oversized file: explain the limitation and do not imply it was recorded.
- An invalid sparse index is regenerated by streaming the authoritative JSONL history. Only incomplete trailing records are ignored; malformed interior records remain errors.

## Acceptance criteria

- [ ] The same supported content produces the same SHA-256 fingerprint under the documented encoding rules.
- [ ] Content retrieved from storage passes hash verification.
- [ ] Repeated identical content does not create duplicate stored blobs within the implemented deduplication scope.
- [ ] Create, modify, delete, and rename sequences reconstruct the correct historical file state.
- [ ] Unified diffs correctly report additions and deletions for representative text fixtures.
- [ ] Empty files, empty diffs, newline edge cases, and missing content are covered by tests.
- [ ] Reconstructing a historical file does not change the current workspace file.
- [ ] A corrupted hash or missing record is surfaced as an error, not silently converted into an empty file.

## Test strategy

Test hashing, storage read/write, deduplication, diff generation/application, and reconstruction independently. Use property-style tests where useful: reconstructing a valid sequence should produce the expected final content, and content hashes should match the recovered bytes. Include corruption and interrupted-write fixtures.

## Compatibility

Any change to blob encoding, hash semantics, path normalization, or persisted references requires a migration plan and tests against existing history.
